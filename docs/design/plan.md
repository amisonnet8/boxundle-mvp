# Boxundle プロジェクト計画書

> **Boxundle** = **Box** + **Bundle**（箱を束ねる）
>
> ステータス：構想段階（ドラフト）
> 作成日：2026-10-23
> 更新日：2026-10-25（方針変更：Boxundle単独で書く／実装はGo／実験は他言語との比較）

---

## 1. 一言でいうと

**外部APIを使う感覚で、自分のシステム全体を扱えるようにする。**

人間が理解するのは「箱」の入出力・テスト・権限だけ。箱の中身はAIが書き、機械が検証する。

---

## 2. 背景と問題意識

今のソフトウェアの道具（DB、プログラミング言語、設定ファイルなど）は、**人間が書き、人間が読む**ことを前提に作られている。

- テーブル、行、変数、関数、IF/WHILE、正規化、インデックスの決め方などは、人間がデータや処理を頭の中で把握するための抽象化である
- その「人間が読める形」が、そのまま**真実（保存・運用される本体）**になっている

AIが設計・実装を担うなら、この前提は変えられる。

- 外部APIを使うとき、私たちは中身のコードを一行も読まず、入出力だけを信用して使っている
- 内部のコードは自分たちで書くので、これまではそうはいかなかった
- **AIが内部を書くなら、内部も外部APIと同じ感覚で扱える**

---

## 3. 基本原則

1. **人間向けの形は「真実」ではなく「表示」にする**
   機械の形を本体とし、人間向けの形は必要なときに取り出して見せる。
2. **人間は書かない。理解して承認する**
   人間の役割は「何がほしいかを決めること」と「それで合っているか確認すること」。
3. **AIが関わるのは設計時だけ**
   実行時はAIなしで、普通のプログラムとして動く。
4. **信頼はテストと検証で得る**
   コードを読んで信用するのではなく、テスト（将来的には証明）で信用する。
5. **人間の理解を、本当に必要なところだけに、信頼できる形で集中させる**

---

## 4. 構想の全体像

### 4.1 箱（サンドボックス）

- プログラムは**箱を束ねて**作る
- 箱は入口と出口以外で外と関われない（サンドボックス）
- 箱の粒度は自在。1つのツールが箱1つでも、100個でもよい
- 箱の中に箱を入れられる（入れ子）。普段は大きな箱として見て、気になったら開けて中の箱を見る

### 4.2 人間に見えるもの

| 項目 | 内容 |
|---|---|
| 入力 | 箱が受け取るもの |
| 出力 | 箱が返すもの |
| 権限 | 外部（ネットワーク、ファイル、時刻等）へのアクセスの有無 |
| テスト | 具体的な入出力の例と、成り立つべき性質 |

人間はこれを**書かない**。AIが提案し、人間が理解して承認する。
人間向けの表示は「書くこと」の制約がないので、例・表・図・文章など、**読むことだけに最適化**できる。

### 4.3 理解の解像度を調整できる

- 重要な処理や不安な部分は、箱を細かく分けて中間を確認する
- 単純な部分は大きな箱1つでAIに任せる
- 「ここをもっと詳しく見せて」と言えば、AIが箱を分けて見せる
- デバッグは、箱を分けて「ここまでは正しいか」を二分探索的に確かめる

箱の区切りは**論理的なもの**であり、将来の実行系では前後を融合して最適化してよい。条件は「そこで止めて見れば、必ずその形になっている」ことが保証されていること。**箱を細かくしても遅くならない**ことを目指す。

## 5. 捨てる概念と、その理由

| 概念 | 何のためにあったか | この構想での扱い |
|---|---|---|
| 行 | 表示、場所の指し示し、差分の単位 | 不要。場所は固定のIDで指す |
| 変数（名前） | 人間が値を覚えて区別する | 識別はIDで行う。名前は意味のラベルとして任意で残す |
| 変数（共有） | 同じ値を何度も使う | データの流れの線として残る |
| 変数（書き換え） | 状態の更新 | なくす。状態は箱の入出力として明示する |
| 関数（区切り・境界） | 人間が理解できる大きさに分ける | 箱が引き継ぐ |
| 関数（再利用） | 人間が直し忘れないように | 不要。共有するかは実行系の最適化判断 |
| IF | 人間が順に読める分岐 | データの行き先の振り分け（route） |
| WHILE | 人間が順に読める繰り返し | 集まりへの操作（filter / map / fold）。必ず終わる |
| 実行の順番 | 手順を物語のように読む | 書かない。依存関係から自動で決まり、並列に動ける |

残すもの：

- **選ぶ・繰り返すという計算そのもの**
- **秩序だった構造の規律**（検証器にとっても解析しやすいため）
- **正しさの保証**（トランザクション等は人間の便利ではなく正しさの問題）

## 6. アーキテクチャ

### 6.1 MVP

```
 AI ──書く──▶ 箱の形式（.bx）＝真実
                 │
                 ├── boxundle check  検証（構文・型・出力の網羅性・権限）
                 ├── boxundle test   テスト
                 ├── boxundle show   人間向けの表示
                 └── boxundle run    実行

 boxundle（Goで作る1つのプログラム）
  ├─ インタプリタ：箱の本体を1ノードずつ評価する
  └─ 標準の箱：文字列・日付・時刻・HTTPなどの汎用部品。Goで実装して組み込み
```

方針：

- **AIが書くのは箱の形式（Boxundle）だけ**。他の言語から変換する入口は持たない
- **真実は箱の形式だけ**。人間向けの形は `show` などで取り出す表示
- **ツールはGoで実装し、単一のバイナリで配る**
- **汎用の機能は、組み込みの標準の箱として提供する**。MVPでは、プロジェクトが独自に外部の部品を足す仕組みは持たない
- 作用（時刻・乱数・ファイル・ネットワーク等）はすべて標準の箱の中でだけ起きる。そのため、権限を静的に検査できるだけでなく、**実行時にも強制できる**

### 6.2 将来

| 段階 | 内容 |
|---|---|
| 外部の部品の追加 | 標準の箱にない部品を、Wasmモジュールとして安全に差し込めるようにする（Goの中で動くWasm実行環境で、サンドボックスとして閉じ込める） |
| Wasmへの変換 | 箱の形式からWasmを生成し、インタプリタより速く動かす |
| 融合最適化 | 箱の区切りを実行時に消して、細かく分けても遅くならないようにする |
| 他の実行先 | 箱の形式はWasmに依存しないため、ネイティブ等を出口として足せる |

- AIにWasmを直接書かせることはしない（保証が抜け落ちるため）

### 6.3 なぜGoか

| 観点 | 理由 |
|---|---|
| 配布 | 単一バイナリで、実験環境にも利用者の環境にも入れやすい |
| 実装をAIに頼みやすい | 言語仕様が小さく、書き方の揺れが少ない |
| 速度 | インタプリタとして実用的な速さが出る |
| 将来のWasm | Goだけで書かれたWasm実行環境（wazero）があり、外部の部品のサンドボックス化に直結する |
| 構文解析 | 文法が小さいので、手書きの再帰下降パーサで十分 |

## 7. 箱の形式の設計方針

### 7.1 AIが書きやすい形の条件

- **前から順に生成しても破綻しない**：どの処理も自分より前のIDしか参照しない。書いている途中でも、そこまでの正しさを確かめられる
- **離れた場所への暗黙の依存がない**：必要な情報はその場に明示する
- **部分だけ直せる**：意味のまとまりに固定IDを振り、ID単位で差し替える
- **書き方が一通り**：迷う余地をなくし、生成を安定させる
- **エラーは機械向け**：構造化され、修正候補付きで返る
- **テキストである**：LLMはバイト列が苦手。人間に読みにくくても、テキストではある

### 7.2 例（説明用に読みやすくしたもの）

在庫が全部足りれば請求書を出して在庫を減らし、足りなければ不足商品を返す箱。

```
box #B7 "注文を処理する"
  in   #i0  注文 { 顧客: ID, 明細: [ { 商品: ID, 数量: 整数, 単価: 円 } ] }
  in   #i1  在庫 { 商品ID → 整数 }
  out  #o0  請求書 { 顧客: ID, 合計: 円 } | 在庫不足 { 商品: [ID] }
  out  #o1  在庫 { 商品ID → 整数 }
  perm なし

  #1 filter #i0.明細 as #e {
       #1.1 lookup #i1 #e.商品
       #1.2 lt #1.1 #e.数量
     }                                          "在庫が足りない明細"
  #2 map #1 as #e { #e.商品 }                   "足りない商品のID"
  #3 empty #1
  #4 route #3
     true {
       #4.1 fold #i0.明細 init #i1 as (#acc, #e) {
              #4.1.1 lookup #acc #e.商品
              #4.1.2 sub #4.1.1 #e.数量
              #4.1.3 set #acc #e.商品 #4.1.2
            }                                   "在庫を減らした結果"
       #4.2 map #i0.明細 as #e { #4.2.1 mul #e.数量 #e.単価 }
       #4.3 fold #4.2 init 0 as (#a, #x) { #4.3.1 add #a #x }   "合計金額"
       emit #o0 請求書 { 顧客: #i0.顧客, 合計: #4.3 }
       emit #o1 #4.1
     }
     false {
       emit #o0 在庫不足 { 商品: #2 }
       emit #o1 #i1
     }
```

実際の形式（[言語リファレンス](../reference/language.md)で定義。例は [examples/](../examples/)）は、これとは細部が異なる。また、装飾を落としてより人間に読みにくくなる可能性がある。ただし**読みにくさは目的ではなく副作用**。圧縮しすぎるとAIにも書きにくくなるため、最適な密度は実験で決める（フェーズ0）。

### 7.3 同じ箱の、人間向けの表示

```
箱「注文を処理する」

受け取るもの
  ・注文（顧客、商品ごとの数量と単価）
  ・現在の在庫

返すもの
  ・請求書（顧客、合計金額）または 在庫不足（足りない商品の一覧）
  ・新しい在庫

権限
  ・外部へのアクセスなし

テスト
  ✓ 在庫が足りる注文 → 請求書が出て、在庫が数量分減る
  ✓ 1つでも足りない商品がある → 在庫不足が返り、在庫は一切変わらない
  ✓ 合計金額 = 数量 × 単価 の総和
```

## 8. テストと検証

- 箱の入出力は、今のテストが最も得意とする単位。テストは箱の外側に「与える入力」と「期待する出力」として書き、`boxundle test` で実行する。CIにもそのまま載せられる
- 作用のある箱（時刻・ネットワーク等）は、テストでは**スタブで出力を固定**する
- テストは3つの役割を持つ
  - **AIへの指示**：テストが通るまでAIが中身を作り直す
  - **人間の理解**：具体例なので、読めば動きが分かる
  - **信頼の根拠**：中身を読まずに信用する理由

### 8.1 AIが自分に都合のいいテストを書く問題への対策

- テストは実装より**先に**作り、人間が承認してから実装に入る
- テストを書くAIと実装を書くAIを分ける
- 例だけでなく、ランダム入力を大量に試すプロパティベーステストも使う（MVPでは例のテストのみ。プロパティテストは後の版で言語に組み込む）

### 8.2 「理解したつもり」での承認を防ぐ

- 典型例だけでなく、境界ケースや意外な挙動を優先して見せる
- 「この理解で合っていれば、このケースはこうなるはず」と人間に確かめさせる
- 前回承認したものからの変化を差分として目立たせる
- AIの説明は、成果物から機械的に導かれた事実に基づかせる（もっともらしい嘘を防ぐ）

### 8.3 将来の発展

- 形式検証（数学的な証明）を後から追加できるようにする
- 検証の段階を表示する：証明済み／テスト済み／未検証
- 契約の穴の指摘：「この条件だと、こういう実装も通ってしまいます」とAIが警告する

## 9. 検証計画：逆転現象は起きるか

### 9.1 仮説

- プロジェクト序盤は、学習量の多い**既存の言語が有利**（新規に書く作業が中心のため。AIはBoxundleを一度も見たことがない）
- 後半は、既存コードの修正・追加・非破壊が中心になり、**Boxundleが有利**になる
  - 読む範囲が箱と隣の箱の入出力だけで済む
  - 書き換えや隠れた状態がなく、変更の影響が箱の中で閉じる
  - ID単位で部分修正できる
  - プロジェクト内に箱が溜まり、それが手本になって形式への不慣れが薄れる
- どこかで**交差（逆転）**が起きる

### 9.2 実験設計

**同じプロジェクトを、Boxundleと他の言語でAIに実装させて比べる。**

| 項目 | 内容 |
|---|---|
| 実験群 | Boxundleだけで実装する |
| 比較群 | 同じ仕様を他の言語で実装する（候補：Python、TypeScript、Go。1つ以上。要決定） |
| AI | すべての群で同じモデル・同じ設定・同じ作業手順 |
| 題材 | 機能を段階的に追加していく中規模のプロジェクト（題材は要検討。§9.6） |
| 試行 | 各群を複数回（例：3〜5回）実行し、ばらつきを見る |

### 9.3 条件をそろえる

違いが「アプリのロジックをどう書くか」だけになるようにする。

- **使える部品をそろえる**：比較群が使えるライブラリは、Boxundleの標準の箱と同等の範囲（文字列・正規表現・日付・ハッシュ・時刻・乱数・ファイル・HTTP）に限定する。それ以外のパッケージは追加させない
- **仕様とテストを共通にする**：各機能追加の仕様と受け入れテストは、言語に依存しない形（入力と期待する出力のJSON）で共通に用意し、各群のプログラムに同じものを流す
- **Boxundleの説明を与える**：AIはBoxundleを知らないので、実験群には言語仕様（利用者向け）をプロンプトとして与える。比較群にも同程度の分量の、その言語の規約を与える
- **ツールをそろえる**：どの群も「書く・検証する・テストする・エラーを見て直す」を同じ回数制限で行う

### 9.4 測定項目（機能追加ごと）

- 受け入れテストが通るまでの試行回数
- 既存機能を壊した回数（回帰：以前の機能の受け入れテストの失敗）
- 使ったトークン数
- 読み込んだコードの量
- 書いた・変更したコードの量
- （Boxundleのみ）`boxundle stats` による、箱の形式で書いた量と標準の箱を使った量

### 9.5 成功基準

結果を見てから解釈しないよう、**実験前に決めておく**。

- 例：「N回目の機能追加以降、回帰の回数とテスト通過までの試行回数が、比較群を継続して下回る」
- Nや「継続して」の定義、比較する言語、試行回数は実験前に確定する

### 9.6 題材の条件

- 機能を10回以上、段階的に追加できる
- 後半の機能追加ほど、既存の機能への変更を伴う
- 標準の箱で足りる（DBなど、MVPにない機能を必要としない）
- 例：在庫・注文管理、簡易な会計処理、テキストの集計ツール など

### 9.7 逆転しなかった場合

- AIがどこで間違えたか、どの機能でつまずいたかの記録から、形式の改善点が分かる
- 書きやすさで逆転しなくても、「壊れにくい」「影響範囲が閉じる」「検証しやすい」という価値は残る

## 11. 未決事項・リスク

- **箱の形式の具体的な文法**：密度、語彙、型の書き方（フェーズ0で検証）
- **比較する言語**：どの言語と比べるか、いくつと比べるか
- **逆転実験の題材選び**：題材によって結果が大きく変わる可能性
- **AIへのBoxundleの教え方**：仕様の与え方で実験群の結果が変わる。比較群との公平性
- **標準の箱で足りない処理**：MVPでは追加手段がないため、題材の範囲を制約する
- **想定外の処理**：箱の形式で書きにくい処理（重い数値計算など）の扱い
- **実行性能**：インタプリタ段階では遅い。融合最適化がどこまで効くか
- **人間の承認の質**：中身を見ずに承認してしまう問題を、表示でどこまで防げるか
- **AIの説明の信頼性**：人間向けの翻訳が正しいことの保証

## 12. 用語

| 用語 | 意味 |
|---|---|
| 箱 | 入出力・権限・テストを持つ、サンドボックス化された処理の単位 |
| 箱の形式 | 箱の中身を表す、AIが読み書きするテキスト形式（Boxundle）。プロジェクトの真実 |
| 標準の箱 | Boxundleに組み込まれた汎用の部品（文字列、日付、時刻、HTTPなど） |
| 地点 | 箱の入口・出口にあたる、データが人間に分かる形になっている点 |
| 承認 | 人間が箱の入出力・権限・テストを理解し、それで合っていると認めること |
| 逆転現象 | プロジェクトの進行につれて、Boxundleが既存の言語より有利になること |

## 13. 名前

**Boxundle**

- 由来：Box（箱）と Bundle（束ねる）を b でつないだ造語。「サンドボックスの箱を束ねてプログラミングする」という構想の核心を表す
- 初見では bundle が隠れていることに気づかれにくいため、README冒頭で「Box + Bundle」と由来を明記する
- 日本語の読み：未定（候補：ボクサンドル）
