# 人間とのやり取り

**人間は、ほぼ「OK」を押すだけで進められ、重要な場面だけはきちんと確認できる**ようにする。原則は3つ。

1. **小さなつまずき**は、原因と「してほしいこと」を短く頼む。人間は「やる／やらない」だけを判断する
2. **人間がする確認**は、準備から結果の取得まで自動にする。人間は見て OK／NG を付けるだけ。1コマンドで、何度でも同じ手順
3. **利用者の目に触れる見え方**を変える・足すときは、変更前後の例を並べた短い資料で了承をもらってから実装する（4章。利用者向けの出力・画面があるプロジェクトだけ）

## 1. 頼む前に、どの種類かを決める

| 種類 | 例 | どうするか |
|---|---|---|
| **小さなつまずき**（原因が分かっている） | サンドボックスで書けない・つなげない、ツールが入っていない、`sudo` が要る、`.claude/settings.json` の変更が要る、`srwr init` で書き換えが要るのに、サンドボックスでは書けない（人間のターミナルで動かす。書き換えが無ければ動かさなくてよい） | 2章の形で頼む。**質問にしない** |
| **些細な判断** | 内部の名前、置き場所、どちらでもよい実装の選び方、テストの分け方、コメントの言い回し | **聞かない。** 決めて進み、`mtqg m add` に「決めたこと・理由」を残す。迷ったら後で変えやすい方を選ぶ |
| **重要な判断** | 利用者の目に触れる見え方（出力・メッセージ・終了コード・データの形式）を変える、依存を足す、取り消せない操作、仕様の文書に誤りや矛盾を見つけた | 必ず聞く。**推奨案を先頭にした選択肢**で聞く（`AskUserQuestion`）。各案の影響を1行ずつ。`mtqg q add` に残す |

**してはいけないこと**
- 「〜できませんでした。どうしますか」と、原因も案も無しに渡す
- 原因を人間に調べさせる（エラーを読む、設定を見る、のは AI の仕事）
- 選択肢だけを並べて、推奨を出さない
- 長い手順を人間に読ませる、手で打たせる
- **調査・検討・議論の最中に、勝手に実装する。** 変更は、人間が依頼したときだけ行う。検討を求められている間は、選択肢と推奨を示し、決まってから適用する。別の作業の流れで見つけた問題は、先に直さず提案する

## 2. 小さなつまずきの頼み方（原則1）

**先に、自分で原因を調べる。** エラー文、`.claude/settings.json`、`.claude/rules/testing.md` の「Bashサンドボックスの落とし穴」、`.claude/rules/srwr-usage.md` の「落とし穴」を見る。原因が分からないうちは頼まない。どうしても分からないときは、試したことを1行で書き、人間に動かしてほしい**確認のコマンド1つ**を出す。

頼むときは、この形で、**5行以内**にする。

```
【お願い】<何が止まったか>
原因：<1行>
してほしいこと：<コピペで動くコマンド1つ、または設定の差分>
やらない場合：<代わりにどう進めるか>
```

例1：サンドボックスの書き込み先

```
【お願い】qsoku lint がキャッシュを書けずに止まりました
原因：~/.cache/golangci-lint がまだ無く、サンドボックスが作れません
してほしいこと：ターミナルで mkdir -p ~/.cache/golangci-lint
やらない場合：lint は飛ばし、vet とテストだけで先に進みます
```

例2：接続先の許可（`.claude/settings.json` は人間が管理するので、差分で示す）

```
【お願い】依存の取得で、許可リストに無い接続先が拒否されました
原因：example.com が network.allowedDomains に無い
してほしいこと：.claude/settings.json の network.allowedDomains に "example.com" を1行足す
やらない場合：この依存は使わず、標準ライブラリで書く案で進めます
```

決まり
- コマンドは**コピペでそのまま動く1つ**（`&&` でつないでよい）。`<ここを書き換える>` のような穴を残さない
- 設定ファイルの変更は、**どのキーに何を足すか**を具体的に書く（人間は貼るだけ）
- 頼むことが複数あるときは、**まとめて1回**で頼む
- 返事を待つ間も、止まらずにできることを進める（「やらない場合」の道で進めてよい）
- 頼んだこと・結果は `mtqg m add` に残す。同じつまずきを2回したら、`.claude/rules/testing.md` の落とし穴に足す

## 3. 人間がする確認（原則2）

| 原則 | 内容 |
|---|---|
| 人間がやるのは「見て判断する」だけ | 準備（ビルド、作業場、データ）、起動、結果の取得は、**すべて自動** |
| 1コマンドで始まる | 人間に渡すのは `qsoku <名前>` のようなコマンド1つと、見るところだけ |
| 何度でも同じ結果 | 毎回、一時ディレクトリに作業場を作り直す。`sleep` ではなく条件を待つ |
| 機械で確かめられることは頼まない | 出力の文字列・終了コード・データの中身・文書の例との一致は、テストで確かめる |

- 人間に頼むのは、**本物の端末・画面でしか分からないこと**（手で押すキー、見た目、対話の感触）だけ
- **確認を頼む前に、その確認の自動化を作る**（`qsokufile` に名前を足す）。手順を文章で渡して代わりにしない
- 頼むときは、この形にする

```
【確認のお願い】<変えたこと>
1. qsoku <名前>
2. <開いたものに対してすること>
3. 見るところ：<何が、どう見えるはずか>
```

- 人間の答えは `AskUserQuestion` の「OK／直す」で受け、`mtqg q add` に残す

## 4. 利用者の目に触れる見え方を変えるとき（原則3）

利用者向けの出力・画面があるプロジェクトで使う。無ければ、この章は消してよい。

**対象**：使い方・出力・メッセージ・終了コード・データの形式・画面など、利用者の目に触れるもの。何が対象かは、プロジェクトがこの章に書き足す。今ある仕様の文書どおりに実装するだけなら、対象外（了承済み）。

**実装を始める前に**、短い資料（置き場所はプロジェクトが決める）に次を箇条書きで書く（1画面に収まる長さ）。

1. 何を変える・足すか、なぜか
2. **変更前と変更後の、実際の見え方の例**（ターミナルの出力そのまま、または画面の画像）
3. 新しく決めること（推奨案つき）
4. 了承してほしいこと

- 人間には2章の形の短い依頼で読んでもらい、`AskUserQuestion` で「了承／直す」を選んでもらう
- **了承されてから、仕様の文書を直し、そのあと実装する。** 了承の内容は `mtqg q add` に残す
- 了承したものと違う見え方を作らない。作ってみて変える必要が出たら、もう一度通す
